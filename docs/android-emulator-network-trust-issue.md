# Android Emulator Network/TLS Trust Issue — Investigation & Fix

## Summary

Remote images (`<Image>`) and `fetch()` calls failed on the Android emulator with:

```
java.security.cert.CertPathValidatorException: Trust anchor for certification path not found.
```

The failure was **not** specific to `<Image>`, and **not** a cleartext-traffic issue (the initial `usesCleartextTraffic: true` fix had no effect because the request was HTTPS, not HTTP). The real cause was a corporate TLS-inspecting proxy (**Netskope**) re-signing all outbound HTTPS traffic from the host machine with its own certificate authority — a CA that Windows trusts (via corporate MDM/Group Policy) but the Android emulator does not.

Two unrelated problems were uncovered and fixed along the way:

1. **The core issue** — emulator doesn't trust the corporate proxy's CA.
2. **A red herring / separate bug** — a stale Metro bundler cache caused the dev client's "Connecting to development server" step to hang indefinitely after a native rebuild.

---

## Root Cause

The Windows machine sits behind a Netskope TLS-inspecting proxy. Netskope intercepts HTTPS connections and re-signs them with its own certificate:

```
subject=CN=randompicturegenerator.com
issuer=C=GB, O=Publicis Groupe, CN=ca.publicisgroupe.de.goskope.com, ...
```

- **Why the browser/host machine works fine:** the Netskope CA is installed in Windows' Trusted Root store via corporate device management.
- **Why the Android emulator fails:** the emulator's NAT networking tunnels traffic through the host machine's network stack, so it also hits the Netskope proxy — but the emulator's Android OS has no idea this CA exists. Every HTTPS request (image loads, `fetch`, anything) fails validation.
- **Why `usesCleartextTraffic: true` didn't help:** that setting only permits plain `http://` traffic. The failing requests were `https://`, so it was irrelevant — the problem is a broken certificate _trust chain_, not cleartext blocking.

This was confirmed conclusively by testing on a physical Android device: with development build installed on physical device connected to its own network (not routed through the laptop's Netskope agent), both `<Image>` and `fetch` worked immediately with zero configuration changes — proving the issue was specific to the emulator's network path through the corporate proxy, not the app code.

## Fix: Trust the Corporate CA in Debug Builds Only

Android 7+ (API 24+) ignores user-installed CA certificates by default — apps only trust the system CA store unless explicitly configured otherwise via a **Network Security Config**. The fix has two parts:

### 1. A config plugin: `plugins/withDebugNetworkSecurityConfig.js`

Since `android/` is regenerated by `expo prebuild` (gitignored, not hand-edited), the fix had to be delivered as an Expo config plugin so it survives every prebuild. It:

- Writes `android/app/src/main/res/xml/network_security_config.xml`
- Sets `android:networkSecurityConfig` on the `<application>` tag in `AndroidManifest.xml`

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <base-config cleartextTrafficPermitted="true">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
    <debug-overrides>
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
    </debug-overrides>
</network-security-config>
```

Key details:

- **`<debug-overrides>` only applies when the app is debuggable** — i.e. dev/dev-client builds. Production release APKs never trust anything beyond the system CA store, so this introduces **no security regression** for shipped builds.
- **`cleartextTrafficPermitted="true"` had to be set explicitly in `base-config`.** A custom `networkSecurityConfig` fully replaces the manifest's default cleartext policy — simply adding trust-anchors silently broke the dev client's plain-HTTP connection to the Metro bundler over the LAN (`java.net.UnknownServiceException: CLEARTEXT communication ... not permitted`). This was caught and fixed by adding the `base-config` block.

### 2. Install the CA certificate on the emulator

The plugin only tells Android _it's allowed_ to trust a user-installed CA in debug builds — the certificate itself still has to be installed on the device.

The certificate was extracted directly from the live TLS handshake (no need to dig through Windows Certificate Manager):

```bash
openssl s_client -connect randompicturegenerator.com:443 -servername randompicturegenerator.com -showcerts \
  | awk '/BEGIN CERTIFICATE/{n++} n==2' > netskope-ca.pem
```

Then pushed to the emulator and installed manually:

```bash
adb push netskope-ca.pem /sdcard/Download/publicisgroupe-netskope-ca.crt
```

**On the emulator:** Settings → Security → Encryption & credentials → Install a certificate → CA certificate → select the file → confirm.

This step is **per-emulator-instance** — recreating/wiping the AVD removes the installed certificate and it must be reinstalled (this happened once during the session when the AVD was recreated from Android Studio).

### Why not install the CA into the emulator's system trust store instead?

This was considered as an alternative that would need zero app changes (a system-trusted CA is honored by all apps automatically). It requires `adb root` + a writable `/system` partition, which only works on certain AVD system images (e.g. "Google APIs", not "Google Play"). The emulator in use here returned:

```
adbd cannot run as root in production builds
```

— a "Google Play" image, which blocks this approach entirely. The debug-only config plugin was used instead since it works regardless of which system image the AVD uses.

## Secondary Issue: Metro Hang on "Connecting to the development server"

After one of the rebuild cycles, the dev client got stuck indefinitely on "Connecting to the development server..." with no error, despite:

- Metro's `/status` endpoint responding instantly
- Raw TCP and HTTP GET requests to Metro succeeding via `adb shell` and `nc`

Tracing the dev client's native source (`expo-dev-launcher`) showed the "Connecting" state stays true until `DevLauncherManifestParser` successfully fetches the app manifest from the **root path** (`/`) of the dev server URL. Testing that specific request directly:

```bash
curl -sv "http://<metro-ip>:8081/"
```

hung indefinitely — and once triggered, it wedged Metro's entire event loop (even `/status` stopped responding afterward). This was unrelated to the certificate/proxy issue; it was a **stale Metro bundler cache**, most likely left over from the repeated `expo prebuild --clean` cycles during debugging.

**Fix:** restart Metro with a clean cache:

```bash
npx expo start -c
```

After this, the manifest endpoint (`/`) responded in ~0.2s and the dev client connected normally.

## Step-by-Step Runbook (For a Colleague Hitting the Same Issue)

If someone else on the team hits the same `CertPathValidatorException` on an Android emulator, here's the exact sequence to reproduce the fix. This assumes the project already has `plugins/withDebugNetworkSecurityConfig.js` and its `app.json` entry (i.e. this repo, or any repo copied from it) — the only thing that's ever missing per-machine is the certificate on the emulator itself.

### 1. Confirm it's the same root cause

Check what's actually signing the HTTPS traffic on the affected machine. Pick any HTTPS host and inspect the certificate chain presented on the wire (bypasses the OS/browser trust store, so it shows the real signer even if the machine already trusts it):

USE GIT BASH

```bash
echo | openssl s_client -connect <some-https-host>:443 -servername <some-https-host> 2>/dev/null | openssl x509 -noout -issuer
```

If the `issuer` is your organization's name or a security vendor (Netskope, Zscaler, Blue Coat, etc.) rather than a normal public CA (Let's Encrypt, DigiCert, Google Trust Services, ...), it's the same class of problem: a corporate TLS-inspecting proxy.

**Exact command used in this investigation** (copy-paste ready — any HTTPS host works, this one was just already in the codebase as the test image URL):

```bash
echo | openssl s_client -connect randompicturegenerator.com:443 -servername randompicturegenerator.com 2>/dev/null | openssl x509 -noout -issuer
```

Output we got, confirming Netskope/Publicis Groupe as the signer:

```
issuer=C=GB, ST=GB, L=london, O=Publicis Groupe, OU=cd850a461d174b1e7a0db97048ad4a25, CN=ca.publicisgroupe.de.goskope.com, emailAddress=certadmin@netskope.com
```

### 2. Extract the proxy's CA certificate

Get the full chain and pull out the certificate that actually signed the leaf (the second certificate in the chain, not the first — the first is the leaf cert for the site itself):

```bash
echo | openssl s_client -connect <some-https-host>:443 -servername <some-https-host> -showcerts 2>/dev/null \
  | awk '/BEGIN CERTIFICATE/{n++} n==2' \
  > netskope-ca.pem
```

Sanity-check it's actually a CA certificate before trusting it:

```bash
openssl x509 -in netskope-ca.pem -noout -subject -issuer -ext basicConstraints
```

Look for `CA:TRUE` in the output. If it says `CA:FALSE`, that's not a CA cert — something about the chain assumption above is wrong for that network (e.g. the proxy sends the chain in a different order), and the request would need adjusting (try `n==1`, or fetch the full `-showcerts` output and eyeball which cert has `CA:TRUE`).

**Exact commands used in this investigation** (copy-paste ready):

```bash
echo | openssl s_client -connect randompicturegenerator.com:443 -servername randompicturegenerator.com -showcerts 2>/dev/null \
  | awk '/BEGIN CERTIFICATE/{n++} n==2' \
  > netskope-ca.pem

openssl x509 -in netskope-ca.pem -noout -subject -issuer -ext basicConstraints
```

Output we got — confirms it's a valid CA cert (`CA:TRUE`), valid until 2034:

```
subject=C=GB, ST=GB, L=london, O=Publicis Groupe, OU=cd850a461d174b1e7a0db97048ad4a25, CN=ca.publicisgroupe.de.goskope.com, emailAddress=certadmin@netskope.com
issuer=C=DE, ST=Frankfurt, L=Frankfurt, O=netSkope Inc, OU=Cert Management, CN=caadmin.netskope.com, emailAddress=certadmin@netskope.com
X509v3 Basic Constraints: critical
    CA:TRUE, pathlen:1
```

### 3. Push it to the emulator and install it

```bash
adb devices                      # confirm the emulator is listed
adb push netskope-ca.pem /sdcard/Download/proxy-ca.crt
```

> **Windows/Git Bash note:** a leading `/sdcard/...` path gets silently rewritten to a Windows path by MSYS's path conversion, which breaks the push. Prefix the command with `MSYS_NO_PATHCONV=1` if this happens:
>
> ```bash
> MSYS_NO_PATHCONV=1 adb push netskope-ca.pem /sdcard/Download/proxy-ca.crt
> ```

**Exact command used in this investigation** (copy-paste ready — this is the one to reuse verbatim on a new/different AVD, after re-running the two commands from step 2 above to regenerate `netskope-ca.pem`):

```bash
MSYS_NO_PATHCONV=1 adb push netskope-ca.pem /sdcard/Download/publicisgroupe-netskope-ca.crt
```

Then, **on the emulator itself** (this part can't be scripted — it requires tapping through the Android Settings UI):

**Settings → Security (or "Security & privacy") → Encryption & credentials → Install a certificate → CA certificate → "Install anyway" on the warning → select `publicisgroupe-netskope-ca.crt` from Downloads.**

### 4. Make sure the app's build actually trusts user certs in debug mode

This should already be true for any build produced from this repo, since `plugins/withDebugNetworkSecurityConfig.js` is checked into source control and runs automatically on every `expo prebuild`. Nothing to do here unless the plugin or its `app.json` registration is missing — in which case, copy `plugins/withDebugNetworkSecurityConfig.js` from this repo and add `"./plugins/withDebugNetworkSecurityConfig.js"` to the `plugins` array in `app.json`, then rebuild:

```bash
npx expo prebuild -p android --clean
npx expo run:android
```

(Stop any already-running Metro/`expo run:android` process first — check `netstat -ano | grep ":8081"` on Windows, or `lsof -i :8081` on macOS/Linux, and kill the owning process before `prebuild --clean`, otherwise the running Metro instance can end up in a stale/conflicting state.)

### 5. Verify

Reload the app and confirm both an `<Image>` load and a `fetch()` call succeed (this project's `src/concepts/NativeImage.tsx` already exercises both, logging `IMAGE LOAD SUCCESS` / `FETCH SUCCESS` to the Metro terminal).

### Gotchas encountered doing this the first time

- **A new/wiped emulator (AVD) loses the installed certificate.** If someone deletes and recreates their AVD in Android Studio, step 3 has to be redone — the cert install is per-AVD-instance, not global.
- **`adb root` doesn't work on all emulator images.** Installing the CA into the emulator's _system_ trust store (which would need no app-level config at all) requires a writable `/system` partition, only available on "Google APIs" AVD images — not "Google Play" images, which reject it with `adbd cannot run as root in production builds`. The debug-overrides plugin approach in this repo works on both, which is why it's the standing solution rather than the system-store approach.
- **If the dev client hangs on "Connecting to the development server..." after a rebuild** with no errors anywhere, that's very likely the unrelated stale-Metro-cache issue described above — run `npx expo start -c` and try again before assuming the CA/cert setup is wrong.

## Physical Device: Does the Same Setup Work There?

**Short answer: yes, the build works fine on a physical device as-is — and whether you need to install a CA certificate on that phone depends entirely on the phone's own network path, not on anything in this project.**

### Why the build itself needs no changes

`plugins/withDebugNetworkSecurityConfig.js` is applied during `expo prebuild`, before the app is ever compiled — it isn't aware of, or specific to, the emulator. Any debug/dev-client APK built from this project (`npx expo run:android` targeting a plugged-in phone, or a debug build distributed another way) already has the same `network_security_config.xml` baked in, trusting user-installed CAs in debug builds. Nothing needs to change to target a physical device instead of the emulator.

### Whether the phone needs the CA certificate installed

This depends on whether the phone's traffic actually passes through the same corporate TLS-inspecting proxy that caused the original issue:

- **Personal phone on home WiFi / mobile data (most common case):** traffic goes straight to the internet and never touches the corporate laptop's Netskope agent or any corporate network gateway. The real public CA chain (Let's Encrypt, DigiCert, etc.) validates normally, exactly like it does for any other app on that phone. **No certificate installation needed** — this was already confirmed empirically: the physical device test done during this investigation worked immediately with zero configuration.
- **Corporate-managed / MDM-enrolled phone:** if the phone itself has a Netskope (or similar) client/profile installed as part of corporate device management, the same interception — and the same `CertPathValidatorException` — could occur. In that case the fix is the same as for the emulator: install the proxy's CA as a trusted certificate on the phone (Settings → Security → install CA certificate). In practice, MDM-managed phones often already have the corporate CA pushed automatically as a **system**-trusted profile as part of enrollment, so this may already work without manual steps — but if not, the debug-overrides config in this project's build already permits trusting a manually user-installed CA too, the same way it does on the emulator.
- **Phone connected to corporate WiFi:** if the office WiFi itself enforces TLS interception at the network gateway (rather than only via a laptop-installed client), any device on that WiFi — phone or otherwise — would see the same rewritten certificates and need the same CA trusted, regardless of whether it's personally owned or corporate-managed.

### How to check quickly

Run the same diagnostic from the runbook above, but from a terminal/app perspective on the network the phone is using (or just try loading `NativeImage` on the phone first) — if `fetch`/`<Image>` work with no changes, the phone isn't going through the proxy and nothing further is needed.

## Notes for the Future

- **No network team involvement needed.** This was fixable entirely as a local, per-machine/per-emulator dev configuration — no corporate network or proxy changes required.
- **Recreating the AVD requires reinstalling the CA certificate** (Settings → Security → Encryption & credentials → Install a certificate). The config plugin itself does not need to be reapplied since it lives in source control and is regenerated automatically by `expo prebuild`.
- **Physical devices** — see the dedicated "Physical Device: Does the Same Setup Work There?" section above; short version: the build needs no changes, and whether the CA needs installing on the phone depends entirely on whether that phone's traffic goes through the same corporate proxy.
